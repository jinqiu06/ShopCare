# ShopCare：21 天开发规划

## 目标与节奏

面向 Agent 后端实习，独立完成一个可运行、可演示、可测试、可解释的电商售后工单 Agent。只做后端，通过 FastAPI 文档、CLI 和运行记录展示。

默认每天投入 4–6 小时，共约 84–126 小时。这是工作量估算，不要求为了日期跳过验收；若某天基础不熟，可以顺延。按 2026-10-24 开始，连续推进的目标完成日为 2026-11-13。Day 7、Day 14、Day 21 都有可以展示的阶段成果，不必等全部完成才开始投递。

当前只有环境、配置和空源码目录。下面出现的模块仅是职责建议，做到当天再创建，不提前生成空文件。

每天建议分配：30–45 分钟理解设计与读必要文档，2.5–3.5 小时编码，45–60 分钟验证与排错，20–30 分钟记录和提交。任务按功能闭环划分，不以代码行数衡量工作量。

## 2026-10-26 起的推进方式调整

- Day 编号作为功能阶段参考，不再把每天清单作为停止线；当天仍有时间且验收通过，就继续下一阶段。
- 每天目标为完成一个有业务意义的闭环，同时至少推进一个需要独立思考的核心实现；不以文档数量、测试数量或代码行数充当进度。
- 开发者负责核心代码：数据模型、业务服务、API、检索、工具、Agent 状态和记忆逻辑。
- 助手负责文档、进度、常规配置维护、格式整理、辅助测试和验证、提交整理；讲解核心设计并审查开发者实现，不直接代写整个核心模块。开发者需要学习测试时结合当前功能讲解，不把所有辅助工作都转交给开发者。
- 今天在应用与配置验收后继续数据库、订单模型和模拟数据；推进速度取决于实际掌握情况，不以进入 Day 2 为由结束当天。
- 2026-10-24 起始日期仅为原先估算；实际 Day 1 为 2026-10-26，后续以进度记录为准。

## 业务边界

主要场景：订单查询、物流查询、退换货资格解释、售后申请草稿、人工确认后提交。

典型对话：用户说“耳机坏了，能换吗？”→ 确认订单 → 查询订单与签收时间 → 检索适用政策 → 必要时补问 → 给出引用政策的方案 → 创建草稿 → 确认后提交。

第一版使用明确标注的模拟订单和自编政策，不连接真实商家系统，不产生真实退款。计算金额、校验订单归属、状态转换和写入权限由程序实现，模型负责理解诉求与选择允许的工具。

明确不做：前端、多 Agent 协作、模型训练、真实支付、任意 SQL 执行、通用浏览器自动化。优先完成一个场景的工程深度。

## 技术路线

- FastAPI + Pydantic：接口与输入输出校验。
- SQLAlchemy + SQLite：订单、售后草稿、申请状态和确认记录。
- LangGraph：状态、工具调用循环、条件路由、执行预算及中断恢复。
- 检索：先做词法检索基线，再加入 embedding 与本地向量索引；优先复用 SQLite/SQLite-vec，不同时维护多种向量数据库。实施前验证 Windows 支持与实际 API。
- 记忆：SQLite checkpoint 保存会话执行状态；应用层独立表管理可查看、更新、删除的长期记忆，两种数据职责分开。
- pytest + Mock：验证程序行为；独立的真实模型评测验证任务效果，两者不能相互替代。
- MCP、Docker：核心闭环稳定后增加，避免阻塞主流程。

## 第一周：业务后端与可引用的检索

### Day 1｜需求落地与应用入口

- 写清三类场景：订单查询、换货咨询、退货申请；定义不支持的请求与统一错误格式。
- 画出订单与售后流程，列出接口草案和首批 10 个验收场景，包含需要澄清的信息。
- 自己编写 FastAPI 入口、健康检查、配置加载；缺失模型配置不影响普通查询服务启动。
- 建立测试入口，验证应用启动、健康检查及配置读取。
- 验收：能用 `/docs` 操作；无 Key 可启动；能解释项目边界与分层理由。
- 交付：需求文档、可启动的最小服务、首批测试和一次 Git 提交。

### Day 2｜数据库与可重建的模拟数据

- 设计用户、订单、订单项、物流和售后申请所需字段及关联；先写表结构说明。
- 实现数据库连接、会话生命周期与初始化；脚本产生至少 20 笔覆盖不同状态的模拟订单。
- 金额使用分或 Decimal，时间明确格式与时区；固定订单 ID，保证演示可复现。
- 初始化必须可重复运行；测试使用独立临时数据库，不能污染演示数据。
- 验收：数据库可从空目录重建，金额与关联字段正确；说明事务与 Session 的作用。

### Day 3｜订单查询与访问边界

- 实现按订单号查询、当前用户订单列表、物流详情，添加输入输出 schema。
- 实现不存在、格式错误、订单不属于当前用户等情况的稳定错误响应。
- 使用固定演示身份或明确标注的开发身份依赖，不把请求体里的用户 ID 当作授权凭证；不扩展完整注册登录系统。
- 覆盖正常查询、错误输入、跨用户访问和分页边界。
- 验收：HTTP 接口可独立工作；用户 A 无法读取用户 B 的订单；Agent 以后复用服务层而非复制逻辑。

### Day 4｜政策知识库与切分入库

- 编写约 8–12 份模拟政策，覆盖商品类别、签收天数、质量问题与非质量问题。
- 政策记录 policy_id、版本、生效日期、适用类别；不同版本需要可以区分。
- 实现加载、清洗、切分与持久化，每个片段保留来源和片段 ID；重复导入不产生重复数据。
- 提前准备约 15 个检索问题及应命中的政策 ID，独立保存，后续扩展为评测集。
- 验收：可以从片段追溯原文，重新入库结果稳定，无需依赖 LLM。

### Day 5｜检索基线与过滤

- 实现可解释的词法检索基线，以及 top-k、类别、生效时间过滤。
- 返回片段正文、来源、版本和检索分数；分数只用于排序，不伪装为答案置信度。
- 处理无结果、失效政策、相似政策和不同商品类别的情况。
- 跑 Day 4 的检索问题，记录 Recall@k 和失败样例，固定基线结果。
- 验收：接口返回可引用证据；过期或不适用政策不会混入结果。

### Day 6｜语义检索与对照实验

- 接入一个实际可用的 embedding 模型，配置独立于对话模型；明确维度、调用失败和凭据加载方式。
- 构建本地向量索引，保存向量与片段 ID 的映射，处理模型版本或维度变化时的重建。
- 比较词法和语义检索；只在失败案例证明有帮助时加入简单混合排序。
- 保留词法模式作为无 embedding 凭据时的可用路径；不将两种模式结果混报。
- 验收：同一批问题上有真实对比记录，能够解释语义检索改善及退化的样例。

### Day 7｜单次模型回答与周验收

- 接入对话模型，输入包含已查询的订单与检索证据，输出结构化答案、引用 ID 和局限。
- 校验模型引用 ID 必须来自本次检索；无证据时明确不足，不能捏造政策。
- 处理超时、无效 JSON、字段不合法；Mock 单测与真实模型试跑分开。
- 保存单次回答基线：同一模型、固定输入、请求耗时与可用 usage 信息。
- 验收：完成“查询订单 → 检索政策 → 单次回答”演示；说明此时还没有自主工具循环。
- 阶段成果：业务 API + 可引用检索 + 单次回答，可录制第一版演示并开始整理投递材料。

## 第二周：Agent、记忆与可靠执行

### Day 8｜工具接口与错误语义

- 将订单查询、物流查询、政策检索封装为模型可调用工具，明确 schema 和工具说明。
- 工具从可信执行上下文获取用户身份，不允许模型改变访问者。
- 工具输出结构化成功或失败结果；区分未找到、输入错误和暂时不可用。
- 测试参数校验、越权访问与工具异常；复用前一周业务服务。
- 验收：不接 Agent 也能独立调用各工具，失败信息可被下一步决策使用。

### Day 9｜LangGraph 有界工具循环

- 设计消息、当前订单、工具结果、步数和终止原因等必要状态。
- 实现“模型选择工具 → 执行 → 观察 → 继续或结束”，而非写死所有调用顺序。
- 约束最大步骤、总模型调用和单次工具输出大小，防止重复查询与无限循环。
- 验证直接回答、需要工具、多工具、无效工具参数和预算用尽路径。
- 验收：可以展示模型因首次结果而选择下一步工具；预算到达后可解释地终止。

### Day 10｜多轮澄清与会话 API

- 实现创建会话、发送消息、读取结果的接口；会话绑定演示用户。
- 场景覆盖多笔相似订单、缺少订单号、用户改口与无法确认订单。
- 缺少写操作所需信息时先询问，不能猜订单；先用非流式响应完成闭环。
- 定义会话状态：处理中、等待用户、已完成、失败，避免并发请求同时推进同一会话。
- 验收：跨多轮能正确补齐信息，不同会话和用户相互隔离。

### Day 11｜短期记忆与重启恢复

- 接入持久化 checkpointer，区分 API 会话 ID 与内部 thread_id，并校验映射归属。
- 在“等待用户补充”时重启服务，继续同一会话；不要只验证进程内字典。
- 控制消息和工具结果增长，先实现有说明的裁剪或摘要策略，保留订单号等关键事实。
- 验证重启恢复、未知会话、跨用户恢复及超长历史。
- 验收：记录可复现的恢复步骤，说明 checkpoint 保存什么、不能替代什么。

### Day 12｜长期记忆的写入与召回

- 实现独立记忆记录：用户偏好、已完成工单摘要；记录用户、来源、更新时间和类型。
- 偏好由用户明确表达或确认后写入；支持查看、更新与删除；数据按用户隔离。
- 仅检索与当前任务相关的记忆，限制条数；当前订单事实始终以数据库为准。
- 验证跨会话召回、旧偏好被更新、记忆删除、其他用户不可见。
- 验收：能演示记忆影响回答，并明确区分历史消息、RAG 文档和长期记忆。

### Day 13｜售后草稿与人工确认

- 实现售后申请草稿，业务代码校验订单归属、商品、时间和允许的状态转换。
- 使用 LangGraph 中断/恢复或等价的显式持久化状态，等待人工确认；实施时核对框架接口。
- 确认接口校验操作者、草稿 ID、草稿版本和待确认状态；拒绝过期或被修改的草稿。
- 覆盖确认、拒绝、修改方案及服务重启后仍处于待确认状态。
- 验收：用户未确认时不会创建正式申请；不能把普通聊天中的含糊“好”误当授权。

### Day 14｜幂等、超时与失败恢复

- 给正式提交设计幂等键和数据库唯一约束，处理重复确认与并发提交。
- 查询工具可按预算重试；写操作必须依赖幂等保障，避免笼统重试。
- 验证“数据库写入成功但响应丢失”的模拟情况，再次请求返回同一结果。
- 记录不含密钥的 request_id、thread_id、工具名、耗时与错误类型。
- 验收：完整售后闭环可演示，重复请求不产生重复申请；能解释恢复边界。
- 阶段成果：具有工具循环、多轮澄清、两类记忆、人工确认和幂等写入的 Agent 后端。

## 第三周：集成、评测与交付

### Day 15｜MCP 工具集成

- 只将只读订单或政策查询工具暴露为本地 MCP 服务，复用已有业务层。
- 在受控本地环境中连接一个 MCP 客户端，再通过适配接入 Agent，验证 schema、超时和失败转换。
- MCP 身份仍由可信服务配置提供，不允许通过工具参数任意指定客户；不开放真实写操作。
- 对比直接 Function Calling 与 MCP 的职责，记录是否增加延迟及运维复杂度。
- 验收：一次完整的 MCP 端到端调用；不能只安装 SDK 就声明完成集成。

### Day 16｜CLI 演示与可观察性

- 编写 CLI：创建/恢复会话、发送问题、展示工具事件、引用和待确认操作。
- 不打印或要求模型输出私有思维过程；展示可验证的工具调用和状态变化。
- 汇总模型调用次数、工具耗时、总耗时及服务实际返回的 token usage；缺失值标记不可用。
- 用固定模拟用户、固定订单与重置数据步骤完成三组演示。
- 验收：无需前端，能在五分钟内展示普通查询、澄清恢复和人工确认。

### Day 17｜固定评测集与执行器

- 将首周案例扩展到 30–40 个，覆盖查询、政策引用、澄清、越权、记忆、工具失败和重复提交。
- 每例定义输入、初始数据库、预期关键行为与判定规则，不强制逐字匹配模型答案。
- 区分可重复的 Mock 回归测试和付费真实模型评测；执行前显示案例数与调用预算。
- 记录模型标识、配置、代码版本、政策版本、运行日期、结果及失败原因。
- 验收：一次命令产生可复查报告；预留至少 10 个样例作为后续验收集，避免全部用于调参。

### Day 18｜有依据的优化与消融

- 分析 Day 17 的失败分布，优先修复最高频的 2–3 类问题，而非同时改所有提示词。
- 用受控变量比较单次回答和 Agent；在适用场景比较记忆开关，检索模式对比沿用固定问题。
- 报告任务完成率、引用有效率、越权拒绝情况、重复提交结果、耗时分布和 token 使用。
- 成本只按实际账单或明确注明的价格估算；模型调用次数与 HTTP 重试次数分开。
- 验收：展示至少一个失败案例、修改理由、回归结果和剩余局限；小样本不宣称统计显著。

### Day 19｜容器化与全新环境复现

- 添加后端 Dockerfile 与运行说明，支持持久化数据库目录；如本机 Docker 不可用，先验证全新虚拟环境并记录未验证项。
- 明确配置、端口、数据库初始化和健康检查；凭据不写入镜像或仓库。
- 在全新数据目录重建样例，验证服务重启后会话和申请仍存在。
- 配置 CI 运行离线测试与代码检查，不需要真实模型 Key。
- 验收：按 README 可以重建环境；Docker/CI 的状态以实际运行结果为准。

### Day 20｜外部试用与缺陷修复

- 邀请 2–3 位同学根据任务说明试用，不预先教他们每一句应该怎么问；人数不足时明确记录实际情况。
- 记录模糊表述、重复发送、拒绝确认、修改诉求等真实交互问题，只使用模拟订单。
- 完成一轮小范围修复和关键回归；检查日志、演示录屏是否包含密钥或个人信息。
- 整理接口契约、状态图、数据表与演示脚本，不再增加大功能。
- 验收：有可追踪反馈及修复记录，不把同学试用描述成商业用户或生产使用。

### Day 21｜最终验收与项目讲解

- 从全新数据库跑三条核心演示，再跑离线回归与保留验收案例；固定代码与数据版本。
- 完成 README：问题、功能边界、安装、示例、架构、测试、评测结果及已知限制。
- 录制 3–5 分钟演示，准备 2 分钟介绍与 10 分钟深入讲解。
- 写简历项目描述，所有技术点能定位到代码，所有数字有报告支持；不虚构业务规模与效果。
- 验收：能独立改一个规则或工具参数、解释一次失败、说明为什么要用 Agent 以及什么步骤不该交给模型。
- 阶段成果：可公开展示的项目版本与投递材料。GitHub 发布和推送按当天明确指令进行。

## 优先级与延期处理

必做：订单/API、政策检索、工具循环、用户隔离、持久化、人工确认、幂等、基础评测和可复现文档。

延期时先减：复杂混合检索、MCP、流式体验、Docker；但必须标注哪些尚未完成。不要删掉身份边界、写入确认或评测来换取更多技术名词。Day 15 可改为补前两周欠账，MCP 放投递后的迭代。

如果每天只能投入 2–3 小时，按验收标准将周期延长到 4–6 周；不要把两天任务机械合并为一天。

## 每天与助手协作的约定

每天可以直接发送：

> 继续 ShopCare Day N。先检查当前代码与上次进度，今天我有 X 小时。按规划拆任务，先讲设计，由我写核心代码，你帮我审查、排错和验收，不直接替我生成整天实现。

- 当天开始：核对代码与验收结果，再确定当天范围，不默认前一天所有任务都完成。
- 当天推进：每次完成一个小闭环；需要学习的概念结合当前代码讲解，不一次性给出整套答案。
- 当天结束：记录完成项、验证结果、实际模型调用、遗留问题和下一步，建议保存到 `docs/progress.md`；第一次用到时再创建。
